# Barkpark Studio · Friday 20 November 2026

Fourteen pull requests merged. Five change what an editor sees: two for a schema's cross-field rules, one for Restore, one for the people list's notice and one for validation marks on a new document. Seven are end-to-end test work, one adds a single CI check, and one was the previous day's News ([#1334](https://github.com/FRIKKern/barkpark-studio/pull/1334)).

## What a person can now do

**Cross-field rules as you type** ([#1336](https://github.com/FRIKKern/barkpark-studio/pull/1336), [#1338](https://github.com/FRIKKern/barkpark-studio/pull/1338)). A schema can hold rules that compare fields, under `cross_validations`. Barkpark checks them on every write; the studio never read them. Now it does.

1. Add a rule to a type's schema with a `name`, a `title`, a `rule`, a `level` and the `fields` it is about. For an end date that may not come before the start: `{field: 'end', operator: 'gte', valueField: 'start'}`.
2. Type an end date before the start. The problem shows under each field in `fields`, at the rule's level, and in the Validation list. The message is the rule's `title`, or its `name` if it has none, as in Barkpark's findings.
3. Leave the end empty. The rule holds: a compare fails only when both sides are numbers, or both are non-empty strings, and the comparison is false. Strings sort by code point, as Barkpark's do.
4. Use `{one: [...]}` for "exactly one of these holds", for example a menu item that links a page or an area, not both and not none. `all` and `any` nest as before.
5. A rule that names no field shows as a problem on the document.
6. Levels: `warning` and `info` show as warnings. Every other level, `warn` included, is an error, as on the server. With no level, a rule is an error.
7. Save. Barkpark's own note on the same rule after the save does not show a second time.

A rule the server cannot evaluate, such as one with an unknown operator or a field the schema does not declare, is skipped quietly here too: no problem, no error. A schema without rules validates exactly as before.

**Field conditions give Barkpark's answers** ([#1336](https://github.com/FRIKKern/barkpark-studio/pull/1336)). `visibleWhen`, `readOnly` and the cross rules use one matcher, and a check against Barkpark's own code found it disagreed both ways. So a field can now show, hide or lock differently than before, each time as Barkpark has it:

- A missing field and `null` are the same value.
- A path through a list skips rows where nothing is found.
- `count_*` counts a list's items or an object's keys; anything else counts as 0.
- `eq`, `neq` and `in` compare lists and objects by their content.
- `all` and `any` work inside a `visibleWhen` or `readOnly` condition.

None of the 145 existing tests that touch these conditions changed result. A table of 91 cases, each answered by Barkpark's code, now checks the studio gives the same answer ([#1338](https://github.com/FRIKKern/barkpark-studio/pull/1338)).

**Restore that cannot put an edit back** ([#1320](https://github.com/FRIKKern/barkpark-studio/pull/1320)). A rich-text edit was kept in this browser because the page reloaded mid-save, and the other editor has since changed the text it touched. Press **Restore**:

1. The card says the unsaved changes to the named fields, from their date, could not be put back because the text changed since, and that they are kept in this browser. Norwegian too.
2. Under it is your kept text, selectable, to copy.
3. Restore is gone for those fields; **Discard** stays. Reload, and the plain card offers the entry again.
4. Discard drops only the fields the card shows. Another kept edit in the same entry, such as a field Restore refused as read-only, stays kept and is offered on the next load.
5. Each field is named once: two kept blocks of the body read "Body".

**No false "Trying to connect…"** ([#1333](https://github.com/FRIKKern/barkpark-studio/pull/1333)). When Barkpark answers the people list with 401 or 403, as it does for a token with no members seat, the studio no longer asks again. The "Trying to connect…" notice no longer shows from about 3 s to 9 s into every load. The people pickers stay empty, as before. A server error is still retried and still shows the notice.

**Validation marks on a new document** ([#1325](https://github.com/FRIKKern/barkpark-studio/pull/1325)). A document made a moment (15 s) before the page loaded stays quiet, with no field marks, until its first edit. That moment is now judged by the page load's time, not the clock while the page draws. The server's page and the browser's first paint show the same marks. Going back to such a document without a reload, its marks show at once if it was edited.

**Harder to break.** The kept-edits Restore test again meets a refused save that must merge both editors' text, so it turns red if typing put back after a reload is lost there; a planted break turned it red 14 of 14 ([#1331](https://github.com/FRIKKern/barkpark-studio/pull/1331)). The test rig's own error checks wait for their error, and the rig now counts a page error queued just as a test ends ([#1332](https://github.com/FRIKKern/barkpark-studio/pull/1332)).

**Tooling.** The end-to-end tests run in 7 parallel groups (shards), each cut off at 60 s; this work aims at under 45 s each. Four fixed sleeps now wait for the event they stood for; the upload-cancel test saves 1.4 to 3.2 s ([#1326](https://github.com/FRIKKern/barkpark-studio/pull/1326)). The resets after each test take about 3.75 s less per suite run ([#1328](https://github.com/FRIKKern/barkpark-studio/pull/1328)). One in-flight-save test went from 7.9 to 5.0 s ([#1330](https://github.com/FRIKKern/barkpark-studio/pull/1330)) and the kept-edits Restore test from 4.1-4.5 to 3.2 s ([#1331](https://github.com/FRIKKern/barkpark-studio/pull/1331)). One of [#1326](https://github.com/FRIKKern/barkpark-studio/pull/1326)'s cuts could hang the editor-chunk test; with a planted late click it hung 8 of 14, so it is back to a fixed 1 s hold, which passed 14 of 14 ([#1329](https://github.com/FRIKKern/barkpark-studio/pull/1329)). The bulk-delete test seeds over earlier leftovers instead of cleaning up first, with no time gain shown ([#1335](https://github.com/FRIKKern/barkpark-studio/pull/1335)). A new CI check, `e2e-all`, passes only when every shard ended in success ([#1324](https://github.com/FRIKKern/barkpark-studio/pull/1324)). It is not required yet: that waits for a change in the repo's settings, after which the seven shard checks can go.

## Where it is slow or rough

- Nobody has looked at cross rules in a browser: no test dataset holds one yet. A rule that names a hidden field shows in the Validation list, but nothing in the form leads to it ([#1336](https://github.com/FRIKKern/barkpark-studio/pull/1336)).
- A studio built before [#1338](https://github.com/FRIKKern/barkpark-studio/pull/1338) skips compare and `one` rules. With `valueField` on an older operator such as `eq`, it can show a wrong problem; it cannot block a save.
- On a slow link, when the editors' code takes longer than 1.5 s to arrive, the image field's Select and the other editor inputs vanish at the form's first update and come back when the code lands. Not fixed yet ([#1329](https://github.com/FRIKKern/barkpark-studio/pull/1329)). The editor-chunk test no longer always checks a click that lands before that code.
- On a just-made document in an open pane, a first write by click only, such as **Add item**, stays quiet until the next keystroke ([#1325](https://github.com/FRIKKern/barkpark-studio/pull/1325)).
- In 56 test runs of the kept-edits Restore test, once no save followed Restore within 15 s. The cause is not known; the test now leaves a short report when that step fails ([#1331](https://github.com/FRIKKern/barkpark-studio/pull/1331)).
- The rig can still miss a page error from a later timer, a frame callback or a network answer that lands after a test ends ([#1332](https://github.com/FRIKKern/barkpark-studio/pull/1332)).
- Shards still hit the 60 s cap with every test passing: 3 of 5 runs on [#1326](https://github.com/FRIKKern/barkpark-studio/pull/1326)'s head. The 7 shards are outgrown, and an 8th is being prepared ([#1328](https://github.com/FRIKKern/barkpark-studio/pull/1328)).
- Not run in a browser: the Restore card's new scene ([#1320](https://github.com/FRIKKern/barkpark-studio/pull/1320)), the new-document marks ([#1325](https://github.com/FRIKKern/barkpark-studio/pull/1325)) and the notice after the people-list fix ([#1333](https://github.com/FRIKKern/barkpark-studio/pull/1333)).
