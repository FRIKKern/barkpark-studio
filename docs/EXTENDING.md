# Extending the studio

For a Sanity developer: where each Sanity habit lives here. Work in your own lane
(`BARKPARK_DATASET=e2e-<you>`, [CONTRIBUTING](../CONTRIBUTING.md)), never in production.

A callback (a role, anything JSON can't say): `form.conditions['<type>.<path>'] = {hidden, readOnly}` in `app/src/studio.config.tsx`, e.g. `conditions: {'post.stage': {readOnly: ({currentUser}) => !!currentUser && !currentUser.roles.some((r) => r.name === 'administrator')}}` (Studio keeps a post's stage closed to all but administrators; the shipped config sets none, its tested copy is `app/src/lib/conditions.fixture.ts`); a field in an array's items leaves the item out (`post.links.title`) and gets its `_key` in `path`. `currentUser` is `{id, name, email, roles: [{name, title}]}` under Sanity's role names: Barkpark's owner and admin are `administrator`, member `editor`, contributor `contributor`, a seat that may not write `viewer`, and a custom Barkpark role keeps its own name (so a custom role named `administrator` or `editor` reads as that Sanity role); with nobody signed in (shared sign-in) it is `null`. Pastes (Paste document, Paste field) at any depth, inside objects by field and inside arrays and Portable Text (custom blocks, inline objects, annotations) by item `_key` and `_type`: Studio keeps a field hidden from you but visible to another role closed to your paste. "Another role" is each the workspace defines, custom ones too, under Sanity's names (Barkpark's `/v1/workspace/roles`, read with your own sign-in); when Barkpark does not say, administrator, editor, contributor, viewer and yours (`app/src/lib/workspace-roles.ts`). To keep a field closed to every role's paste, make it read-only. While Studio does not know your role (its check failed or has not answered), every field with a role rule stays closed, and a document of a type with a role rule, or with unsaved changes kept for it, says so with Retry; with no role rule and nothing kept, nothing is closed and nothing is said. A paste lock is decided by role, comparing those roles: a rule keyed on one person's email or id is no paste lock, so use a role or read-only for that. The `hidden` here is asked for each of those roles on the same data, on the document as it is and as the paste leaves it; a read-only field (the schema's `readOnly`, as Sanity's, or one here, on the document as it is) keeps its value too. Hidden from every role (`visibleWhen`, the schema's `hidden`, `hidden: true`, `({parent}) => parent?.kind !== 'url'`) is data, and pastes as on main; so does everything with shared sign-in. A rich-text object block is walked as its dialog shows it, with the dialog's schemas (a paste waits for them and, if they don't load, is refused and writes nothing): where the dialog's only editor holds the whole block and is locked (`<field>.code.code`, `<field>.image.image`), the whole block stays. An item only the copy has comes in whole; an item the paste removes stays only while it holds such a value (`app/src/lib/paste-locked.ts`). With no rules a paste writes what main writes. Sanity's paste checks top-level read-only fields only. Paste document names the top-level read-only fields it skips (three, then "and N more"). A read-only field takes no typing, array or Portable Text edit. One rule decides it on every surface (`fieldState`; `app/src/lib/fieldrule-scan.test.ts` lists them, and `mayWrite` decides each write): the form, paste, the Freeform canvas (read-only while a field it holds is read-only for you: a body region, a bound field block, or, with no layout, a rich-text field; not drawn while one is hidden from you, and the form shows the rest; `app/src/lib/form-lock.ts`), and the save, which refuses a change you make by hand to a field read-only for you and says so (`app/src/lib/doc-lock.ts`); a clash's "Keep mine" too, and the card then offers theirs and shows your text to copy. Unsaved changes kept in this browser for such a field are not put back: the pane names the fields, and they stay kept. A document action's `set` is the action's code: the document lock only. Until Barkpark has said who you are, a field with a callback is read-only, and hidden if its `hidden` is one. A group tab whose fields are all hidden goes. **A form convenience, not access control:** the API, imports, document actions and Barkpark's roles still decide what is written (`app/src/lib/conditions.ts`) |

## The Dashboard

`dashboard` in `app/src/studio.config.tsx` turns the Dashboard tool on (`/dashboard`, after
Structure in the navbar; Structure stays the tool `/` opens). Without `widgets` it shows the
default five. A deployment that sets `VITE_STUDIO_TOOLS` gets it only by naming `dashboard`.

```tsx
dashboard: {
  widgets: [
    {type: 'drafts'}, // every unpublished change, newest first
    {type: 'recent', limit: 8}, // the newest edits across the desk's types
    {type: 'tasks'}, // open tasks assigned to you (J66)
    {type: 'scheduled'}, // the next scheduled publishes (J40)
    {type: 'members'}, // the workspace's people, a dot on who is online
    {type: 'documentList', title: 'Latest posts', types: ['post'], order: '_createdAt desc', limit: 5, createNew: true},
    {name: 'house-style', title: 'House style', component: HouseStyle, layout: {width: 'small'}},
  ],
},
```

`documentList` is Sanity's widget: `types` (all the desk's when left out), `order` (GROQ's,
default `_createdAt desc`), `limit` (default 10, at most 25), `createNew` (a "Create new"
button when there is one type; off for a read-only seat), `createButtonText`. A custom widget
is `{name, component, title?, layout}`: any React component, drawn in a card. Every widget
takes `title` and `layout: {width: 'small' | 'medium' | 'large' | 'full'}` (1, 2, 3 columns
or the row; one column on a phone); `{type: 'projectInfo'}` names the workspace, project and
dataset. Rows open their document in Structure. Shapes and defaults: `app/src/lib/dashboard.ts`.

What it reads (`app/src/lib/dashboard-data.ts`): one GROQ read per document widget for any
number of types, a second when drafts are among the rows; then it listens, and a live frame
(a document's or a task's) is put into the rows without a read. Nothing polls. A list of the
last created is right or, with very many drafts open on old documents, shorter. Barkpark's documents do not say who
edited them last, so the drafts widget is everyone's; with shared sign-in the tasks widget
lists every open task and says so.

## Field types and validation

Every field type, its options, Barkpark's validation keys (`required min max pattern unique
level message`) and what Barkpark ignores: Barkpark's
[schema reference](https://github.com/FRIKKern/barkpark/blob/main/docs/contracts/schema-reference.md).
The form draws the types in `app/src/lib/schema-vocab.ts`; copy a field from
`fixtures/barkpark-schema/post.json` (its slug has a `pattern`). Barkpark stores a
misspelled key and never reads it: VS Code checks these files against
`fixtures/barkpark-schema.schema.json` (generated from `schema-vocab.ts` by
`scripts/fixture-schema.mjs`, kept in step by a unit test), and `seed-barkpark` refuses one
that fails it.

A datetime's `options.displayTimeZone` (an IANA name, `America/New_York`) shows and reads its
time on that zone's clock, with Sanity's zone button after the title; `allowTimeZoneSwitch: false`
keeps it there, and `true` alone gives the button in local time. The value stays a UTC instant.

Sanity's other rule builders are rule keys, checked as you type in Sanity's words (an error
blocks Publish): `length` (characters, items or blocks), `precision`, `greaterThan`, `lessThan`,
`positive`, `negative`, `lowercase`, `uppercase`, a pattern's `name` and `invert`,
`assetRequired` (image, file), and on a date or datetime a `min`/`max` date (`"2026-01-01"`,
`"now"`). They run in the studio only, as Sanity's: Barkpark stores them and never runs them.
It does check a `pattern` itself and reads no `invert`, so an inverted pattern is refused (or
warned) on save for the values it allows: keep it out of a schema until Barkpark reads it.
Examples: `day`, `at`, `width`, `height`, `zip`, `photo` in `fieldTypes.json`.

Sanity's `Rule.custom` (a field's or the whole document's, with `context.document` /
`context.parent`, answering at once or with a Promise) is `document.validation(type)` in
`app/src/studio.config.tsx`: `[{path?, level?, validate(value, {document, parent, path})}]`.
A Promise holds Publish ("Validating…", 10 s at most); a throw is an error. These run in the
studio only, as Sanity's do: an API write or an import is checked by the schema's data rules alone.

A rule that compares fields and needs no code belongs in the schema instead, as data both sides
check: `cross_validations` `[{name, title, rule, level, fields}]`, `rule` a condition as in
`visibleWhen` or `all` / `any` of them. Barkpark checks it on every write; the studio shows a
broken one as you type, under each field in `fields` (`app/src/lib/cross-rules.ts`). A rule the
server can't evaluate (an unknown operator or field) is skipped on both sides.

## Removing a type

Delete its file in `fixtures/barkpark-schema/`, then
`BARKPARK_DATASET=e2e-<you> node --env-file=.env scripts/seed-barkpark.mjs --remove-type <type>`.
It's a dry run until you pass `--yes`. It refuses when documents of the type remain, unless
you pass `--with-docs`, which deletes them first. Production needs `--production`.
